# ステージ生成・検証ツール

`levels.js`（本編50ステージ）と `ura-levels.js`（裏1〜30）は手書きではなく、
ここのスクリプトで生成・検証しています。裏ステージのCSS（もみじのマス絵と
金属光沢の選択ボタン）も生成物です。

## 1. 候補プールを作る（数分かかります）

```sh
python3 generate-pool.py pool.json
```

**正解の経路を先に引き、止めたい位置にお邪魔ブロックを置いていく逆算方式**で盤面を作ります
（`carve()`）。各手で「行けるところまで」ではなく途中で止めたい場合、その一つ先にブロックを
新設して停止理由を作ります。経路が通らなかったマスも最後にブロックへ変換します。
経路上でも停止理由でもないマスなので、変換しても経路は変わりません。

ランダムにブロックを置く方式も試しましたが、解ける盤面がほぼブロック0〜1個のものに偏り
（7x7で成功例の平均1.1個）、盤面がスカスカになるため採用していません。

作った盤面は改めて全解探索にかけ、難易度指標（マス数・ブロック数・迷いどころの数・
探索ノード数・解の総数）を記録します。数十秒で10万件規模のプールができます。

環境変数: `PER_SIZE`（盤面サイズごとの上限件数）、`BUDGET_SCALE`（時間予算の倍率）、
`P_LO`/`P_HI`（早期停止の確率＝ブロックの作られやすさ）。

## 2. 50ステージを選んで levels.js を書き出す

```sh
python3 build-levels.py pool.json ../levels.js
```

難易度スコアがなだらかに上がるよう50件を選びます。一本道の盤面とブロックが少なすぎる盤面は
候補から除き、終盤は迷いどころが3つ以上ある盤面だけを使います。書き出す前に全件を再生検証します
（新ルールで手順を再生して全マスが塗られるか、空振りの手が混ざっていないか、
盤面が連結しているか）。

## 2-a. 後半だけを作り直して難しくする

序盤（本編1〜10・裏1〜10）はルールを覚える帯なので触らず、後半だけを選び直したい
ことがある。そのための入口が `rebuild-late.py`。

```sh
python3 rebuild-late.py pool.json scattered.json   # levels.js と ura-levels.js を書き換える
```

既存のファイルから残す分をそのまま読み、本編11〜50と裏11〜30だけを候補プールから
選び直す。

順位で切ると帯の変わり目で難度が段差になる（前の帯の一番上より、次の帯の一番下が
低い）ため、**「この番号はこのくらいの難しさ」という狙い値を先に決めて、そこへ
いちばん近い候補を取る**方式にしている（`pick_targets`）。おかげで通し番号どおりに
難度が上がる。

盤面を広げるだけだと歩く手間が増えるだけなので、**迷いどころ（正解手順上で2方向以上
選べた回数）の下限**を帯ごとに上げるのが効く。

## 2-b. 裏ステージ（裏1〜50）を作る

裏ステージは本編50ステージをすべてクリアすると解放される、石が点在する難しい盤面です。
10面ずつ5帯（緑・黄・赤・茶・黒のもみじ）。

```sh
python3 generate-scattered.py scattered.json     # 候補プール（数分かかります）
python3 build-ura-levels.py scattered.json ../ura-levels.js
```

`generate-pool.py` の `carve()` は「経路が通らなかったマスをまとめて石にする」ため、
石が一枚岩の壁になり、歩ける場所が細い通路に狭まります。石が多く見えても分岐が無いので、
見た目ほど難しくなりません。

そこで `generate-scattered.py` では**経路と石を同時に、後戻りありで探索**します。
各手は「行けるところまで進む」か「途中で止めて、その一つ先に石を置く」のどちらかで、
未通過のマスが分断された時点でその枝を捨てます（連結性の枝刈り）。取り残しのポケットが
生まれないので盤面は「経路 + 止まる理由の石」だけで埋まり、石は1〜2マスの粒として
散らばります。石がつながる数は `MAX_CLUMP`（既定2）までに制限しています。

作った盤面はより短い解が無いかを調べ、最短手順に置き換えてから記録します
（`minimise()`）。画面の「最短N手」を正しく出すためです。打ち切りに達した盤面は
`minproven` が false になり、`build-ura-levels.py` の候補から外れます。

環境変数: `PER_SIZE` / `BUDGET_SCALE` / `MAX_CLUMP` / `NODE_CAP` / `MIN_NODE_CAP`。

`build-ura-levels.py` は、石がまばら（孤立率45%以上・最大の塊2マス以下）で迷いどころが
多い候補だけから、難易度がなだらかに上がるよう選びます。書き出す前に全件を再生検証します。

裏31〜50 は `rebuild-late.py ura-late` で足します（2-a 参照）。この帯は「進める方向が
多いこと」を難しさの主役にしているので、迷いどころの合計ではなく**1手あたりに選べる
方向の数**（`branch()` = 1 + 迷いどころ ÷ 手数）で並べ、その上位20面を採ります。

    SIZES=13x12,13x13,14x12 BUDGET_SCALE=7 PER_SIZE=400 \
      HOLE_LO=0.05 HOLE_HI=0.20 P_LO=0.20 P_HI=0.55 \
      python3 generate-scattered.py big.json
    python3 rebuild-late.py ura-late big.json

`generate-scattered.py` は `SIZES` で盤面サイズを、`HOLE_LO`/`HOLE_HI` で石の割合を、
`P_LO`/`P_HI` で早期停止の確率を選べます。大きい盤面は1面あたり数十秒かかるので、
14x12 まで含めると通しで1時間以上かかります。

できあがりの帯（手数の中央値）:

| 帯 | 手数 | マス数 | 1手あたりの方向 |
|---|---|---|---|
| 裏1〜10 緑 | 39〜43 (40) | 69〜91 | — |
| 裏11〜20 黄 | 44〜58 (47) | 87〜120 | — |
| 裏21〜30 赤 | 55〜70 (62) | 113〜127 | — |
| 裏31〜40 茶 | 66〜73 (69) | 125〜139 | 1.16〜1.20 |
| 裏41〜50 黒 | 66〜74 (70) | 125〜139 | 1.19〜1.23 |

裏31以降はヒントを1ステージにつき1回しか使えません（`game.js` の `hintLimit`）。

## 2-c. 裏ステージの見た目（もみじ・金属光沢）を作る

```sh
python3 gen-ura-style.py          # style.css を書き換える
python3 gen-ura-style.py --check  # ずれていれば終了コード1
```

`style.css` の「自動生成」マーカーで囲まれた範囲だけを差し替えます。マーカーの外は
手書きなので、この範囲に手で書き足さないでください。

* `momiji.py` … もみじの葉をSVGで組み立てます。極座標で葉の裂片と切れ込みをたどり、
  縁にぎざぎざを付け、上の葉ほど大きく下ほど小さくなるようにします。輪郭の先端と葉柄の
  先が正方形の角にちょうど触れるよう、縦横それぞれ引き伸ばして枠いっぱいに収めます。
  帯ごとの色は緑（裏1〜10）・黄（裏11〜20）・赤（裏21〜30）。
* `metal.py` … ステージ選択ボタンの縦縞クローム調グラデーションを作ります。同じ色相の
  明暗を12段に刻んだ `linear-gradient(90deg, ...)` です。

どちらも CSS の `data:image/svg+xml,...` として埋め込むため、追加の画像ファイルは
ありません。

## 2-d. アカウント（ログインと、ユーザーごとの保存）

進行状況はふだんこの端末の localStorage に置くだけだが、ログインするとアカウントにも
保存され、別の端末でも続きから遊べる。認証と保存は Supabase（給与・勤怠システムと
同じプロジェクト）を使う。

```sh
# Supabase の管理画面 → SQL Editor に貼って一度だけ実行する
cat supabase-setup.sql
```

`line_puzzle_progress` テーブル（1ユーザー1行・進行状況は jsonb）と、自分の行だけを
読み書きできる行レベルセキュリティ(RLS)を作る。anon キーは公開されるので、RLS が
無いと誰でも他人の記録を読めてしまう。

SQL のほかに、管理画面で2か所の設定が要る（SQLでは変えられない。詳しくは
`supabase-setup.sql` の冒頭に書いてある）。

* Authentication → Providers → Email の **Confirm email をオン**
  （新規登録の確認メールを出すため。オフだと登録した瞬間に入れてしまう）
* Authentication → URL Configuration → **Redirect URLs** に公開URLを登録
  （メールのリンクから戻ってくる先。登録が無いとリンクを開いてもゲームに入れない）

クライアント側は `../cloud.js`。supabase-js は 200KB あり、この一枚のゲームには
重いので使っていない。必要なのは「登録・ログイン・トークン更新・1行の読み書き」だけ
なので fetch で直接 REST を叩いている（`build-single-file.py` で1ファイルにまとめる
ときも、そのまま埋め込める）。

* 登録: ユーザー名 / メールアドレス / パスワード
* ログイン: メールアドレス + パスワード（メールが本人確認の宛先なので、
  パスワード再設定メールが使える。ユーザー名は画面に出す表示名）
* 新規登録すると確認メールが届き、そのリンクを開いて初めて登録が完了する。
  リンクは `…/line-puzzle/#access_token=…&type=signup` の形で戻ってくるので、
  `cloud.js` の `readAuthRedirect()` が読み取ってログイン状態にし、URLからは消す
* アカウント画面から**ユーザー名・メールアドレス・パスワード**を変えられる
  * ユーザー名 … その場で変わる
  * メールアドレス … 新しいアドレス宛の確認リンクを開いて初めて変わる
  * パスワード … 現在のパスワード / 新しいパスワード / 確認 の3つを入力する。
    先に現在のパスワードで入り直して確かめてから差し替えるので、端末を
    横取りされてもパスワードは変えられない
* 今のパスワードが分からない人向けに、ログイン画面の「パスワードを忘れた」は
  メールのリンク方式のまま残してある。そのリンクから開く画面は、性質上
  「新しいパスワード + 確認」の2つだけを聞く
* 同じメールアドレスで2つ目のアカウントは作れない。Supabase が auth.users の
  メールアドレスを一意にしている。ただし確認メールを送る設定のときは、登録済みの
  メールでも Supabase は成功のような形で返す（他人のメールが登録済みかを外から
  調べられないため）ので、`identities` が空かどうかで見分けて案内している
* ログインしていない間の記録は、あとでログインした時にそのアカウントへ引き継ぐ
  （同じステージの記録が両方にあるときは、★が多いほう・同数なら手数が少ないほうを残す）
* 同じ端末で別のアカウントに切り替えても混ざらないよう、保存先の名前に
  ユーザーIDを付けている（`linePuzzle.progress.v1:<user id>`）

## 3. ブラウザで通しテストする

```sh
# リポジトリのルートで
python3 -m http.server 8777 --bind 127.0.0.1 &
node tools/test.mjs      # 要 playwright
```

登録不要で始められること、全50ステージの自動クリア、オートセーブと再開、
各ボタンの動作と配置、クリア後の再チャレンジ、★が黄色の塗りつぶしであること、
通過済みマスに戻れないこと、スワイプ操作、全ステージにお邪魔ブロックがあること、
行き止まりのお知らせ、チュートリアルの中身、アイコンが単色かどうかを確認します。

裏ステージについては、30面すべての再生検証と石のまばらさ、本編50ステージを
クリアするまで解放されないこと、解放後に遊べて記録が本編と別に残ることを確認します。

アカウントについては、本物の Supabase を叩かずに済むよう、認証と保存の2つの
エンドポイントだけを `page.route()` で肩代わりする偽のバックエンドを使います。
登録・ログイン・間違ったパスワード・ログイン前の記録の引き継ぎ・クラウドへの書き戻し・
別端末からの続き・クラウドが落ちている時をひと通り確認します。

確認メールの流れも通しで確認します。偽バックエンドが送ったメールを控えておき、
その `#access_token=…&type=…` を付けたURLを開くことで「メールのリンクを押した」を
再現しています。新規登録の確認、リンクを開く前はログインできないこと、同じメールで
2つ目を作れないこと、ユーザー名・メールアドレスの変更、パスワードの変更（確認欄の不一致・現在のパスワードの
間違い・正しく変えられること）、忘れた場合のメール経由での決め直しまでを見ます。

全ステージを実際に自動プレイするため、通しで8〜10分ほどかかります。

## 4. 版数(?v=)を付け直す ← 公開前に必ず

```sh
python3 stamp-assets.py          # 付け直す
python3 stamp-assets.py --check  # ずれていれば終了コード1
```

対象は `style.css` / `levels.js` / `ura-levels.js` / `cloud.js` / `game.js` です。

GitHub Pages は静的ファイルをブラウザにキャッシュさせるため、版数を付けずに更新すると
利用者には古い CSS/JS が読み込まれ続け、変更が反映されません。

手で番号を増やす運用は付け忘れます（このリポジトリでも過去に一度漏れています）。
そこで**ファイルの内容そのもののハッシュ**を版数にしています。中身が変われば版数も必ず
変わり、中身が同じなら版数も変わりません。`tools/test.mjs` でも版数と中身の一致を
確認しているので、付け忘れるとテストが落ちます。

## 6. ブロックフィットパズルの盤面を作り直す

`bf-levels.js`（全50ステージの盤面+ピースデータ）は手書きではなく、
`gen-bf-levels.mjs` で生成しています。

```sh
node tools/gen-bf-levels.mjs > bf-levels.js
```

**空の盤面にピースを1つずつ隣接させながら置いていき、置けた場所の集合を
そのまま盤面の形として採用する**逆算方式で作ります。この方法だと生成した
時点で必ず解けることが保証できます（`solution` の通りに置けば埋まる）。

ステージが進むほど、ピースの個数・大きさ（4→5→6マス）・回転が必要な
ピース(左右非対称な形)の比率を連動して上げ、難易度をなだらかに上げます。
盤面が細長くなりすぎるとスマホ画面に収まらずセルが小さくなりすぎるため、
重心に近いマスを優先して育てる+縦横のマス数に上限を設けて、丸みのある
塊状の盤面になるようにしています。

生成時に接続性・重複なし・完全被覆・盤面サイズの上限を検証し(`validateStage`)、
失敗したステージはシードを変えて作り直します。標準エラー出力に各ステージの
盤面サイズ・ピース数・平均ピースサイズ・回転が必要なピースの割合を出すので、
難易度カーブがなだらかかを目視で確認できます。

## 8. 深海迷路のステージを作り直す

`dsm-levels.js`（全50ステージ分の海底迷路データ）は手書きではなく、
`gen-dsm-levels.mjs` で生成しています。

```sh
node tools/gen-dsm-levels.mjs > dsm-levels.js
```

グリッド上にランダムDFS/Prim's法混合で全域木(スパニングツリー)を作り、
STARTとGOALはその木の直径(最も長い経路)の両端に取ります。木なので
START→GOALの経路は構造上かならず一意に存在し、それ以外の枝がそのまま
行き止まり・ダミールートになります。次数2のノード(素通りする点)は
Catmull-Romスプラインで1本のチェーンにまとめ、直線だけでなく曲線・S字・
蛇行を自然に作ります。チェーンの点列(`segments[].points`)は描画にも
当たり判定にも同じものを使うため、見た目とヒットボックスはズレません。

ステージ番号を0〜1に正規化し、`t^0.62` というカーブ(指数が1未満=序盤ほど
速く上がる)へ通してから、グリッドの大きさ・分岐のできやすさ(`branchBias`)・
閉路(周回ルート)の量・斜め通路の確率・通路幅(狭くなる)を連続的に補間して
います(`tierFor()`)。Stage1(t=0)は指数によらず必ず `te=0` になるため
最小パラメータのまま据え置かれ、Stage2以降で一気に(かつ滑らかに)難易度が
立ち上がります。段階(tier)で区切らず連続にしているので、「1ステージ増えた
だけで急に難しくなる」段差が生まれにくく、`TOTAL_STAGES` を増やして
Stage 51〜を足すのも `tierFor()` の式をそのまま伸ばすだけで自然に繋がります。

Stage 31以降は `fogRadius`(視界半径。ワールド座標のpx)をステージデータに
持たせ、船の周り以外を画面座標のラジアルグラデーションで暗くします
(`drawFog()`)。ステージが進むほど半径を絞って、終盤ほど「先が見えづらい」
深海らしさを強めています。テーマの地色(`THEME_COLORS`)自体も7帯目
(Stage31〜)から段階的に暗く・彩度を落としています。

生成後、**ラスタライズ+BFSで実際にSTARTからGOALへ到達できるかを検証**
します(`validateStage`。ゲーム本体の当たり判定と同じ「中心線までの
距離 <= 幅/2 - 船の半径」を使うので、生成時の検証とプレイ時の判定が
食い違うことはありません)。検証に落ちたステージはシードを変えて
作り直すので、書き出される全ステージは常にクリア可能です。

標準エラー出力に各ステージの盤面サイズ・正解ルートの長さ・行き止まり数・
分岐数・カーブ数・通路幅・視界半径を出すので、難易度カーブがなだらかかを
目視で確認できます。ステージデータを調整したときは、このスクリプトを
再実行するだけで全ステージの再検証になります。

### 敵キャラ(`stage.enemies`)

各ステージには `enemies: { urchins, swimmers }` が付き、`pickEnemies()` で
生成します。触れると即ゲームオーバー(そのステージの最初からやり直し)。

- **Stage1〜10**: 固定の「ウニ」。行き止まり(次数1のノード)には見た目を
  目立たせた「フサフサ」型、道中の壁際には「触手」型を配置します。
- **Stage11〜20 / 21〜30**: ゆっくり/速く泳ぐ「深海ピラニア」
  (提灯付きアンコウ型 / 棘状背びれ型)。
- **Stage31〜40 / 41〜50**: ゆっくり/速く泳ぐ「ウツボ」
  (ヒカリウツボ / ノーマルウツボ)。

遊泳する敵(ピラニア・ウツボ)は探査船と違って壁の当たり判定を持たず、
通路の外(壁の中)も自由に横切って泳ぐ想定なので、`waypoints` はノード
座標をランダムに繋いだだけの巡回ルートです(壁を避ける必要がない)。

固定のウニは違います。「道中の端」に置く触手型ウニは、当たり判定の
半径が通路の片側をほぼ塞いでしまうことがあるため、`validateHazards()`
で「ウニの当たり判定を避けてもSTART→GOALへ到達できるか」を
`validateStage()` と同じラスタライズ+BFSで追加検証しています。ここで
落ちたステージ(=避けようがない配置になったもの)もシードを変えて
作り直すので、書き出される全ステージは常に「ウニに一度も触れずに
クリアできる」ことが保証されます。当たり判定の半径を変えるときは、
`tools/gen-dsm-levels.mjs` の `TENTACLE_HIT_MUL` と
`deep-sea-maze.js` の `checkEnemyHit()` 内の同名の掛け率を必ず
同じ値に揃えてください(生成時の安全確認とプレイ時の判定が食い違うと
この保証が崩れます)。

### 迷路の構図(意図して入れている3つの仕掛け)

全域木のままだと「行き止まりだらけの一本道」になり、分岐を選ぶ楽しさが出ません。
かといって閉路をランダムにばらまくと、**どの枝を選んでも同じ道に合流して
しまい分岐の意味が消えます**(以前それで作り直しました)。そこで閉路は
**意図した2本だけ**を足しています。

1. **回り道 + 通せんぼ** (`addDetourLoop` → `placeBlockerUrchin`)
   正解ルートの1辺を選び、その辺を通らずに戻れる箱型の回り道をグリッド上に
   足します。そのうえで、**その辺の上に通路を完全に塞ぐ大きさのウニ**を置く。
   まっすぐ行くと塞がれていて、回り込むとウニの先に出られる、という構図です。
   ウニの半径は「当たり半径(r×1.15)+船の半径 ≧ 通路の半幅」から逆算して
   いるので、左右どちらからも抜けられません。

2. **だまし分岐** (`addFalseLoop`)
   プレイヤーが必ず通る分岐点(次数3以上)の、2本の枝の先どうしを繋ぎます。
   「3本に分かれていて、1本を選んで進んだら、ぐるっと回って同じ分岐点の
   別の枝から戻ってきた」という構図になります。

3. **道中の半身ウニ** (`placeTentacleUrchins`)
   緑の触手つきウニは、正解ルートの近くにある区間を優先して選びます
   (行き止まりにしか居ないと、ゴールまでの道のりが簡単すぎるため)。
   壁際いっぱいに押し込むので体が通路に半分はみ出し、ギリギリ避けて通ります。
   さらに**左右にウニ3個分(直径×3)ゆっくり往復**します。

揺れ幅は `validateHazards()` が「揺れて通る範囲すべて」を危険とみなして
検証し、通れなければ 0.6 倍ずつ詰めます。こうしておけば「揺れの向こう側で
待たされて詰む」ことが無く、**どの瞬間でも通り抜けられる**ことを保証できます。
通路が狭いステージほど揺れ幅は自然に小さくなります。

`stats.detourExtra` は「ウニを避けると道のりが何%伸びたか」です。ここが 0 の
ままなら通せんぼが効いていないので、生成をやり直します(それでも見つから
なければ条件を緩めます)。生成ログにも出ます。

生成だけを試すときは `DSM_ONLY=26 node tools/gen-dsm-levels.mjs`(そのステージ
だけ)、`DSM_TRACE=1` を足すと何回目の種で通ったかが出ます。

### 全50ステージのクリア可否チェック

`dsm-levels.js` を作り直したら、**必ず** `tools/dsm-clearable.mjs` を流して
ください。生成時の検証とは別に、**本番のコードそのもの**で50ステージすべてを
確かめます。

```
python3 -m http.server 8777 &
PW_CHROMIUM=/opt/pw-browsers/chromium node line-puzzle/tools/dsm-clearable.mjs
```

見ているもの:

- 通れる／通れないは実行時の `isPassable()` をそのまま呼ぶ(テスト側に判定を
  書き写さないので、本番とずれたら必ず落ちます)
- ウニの当たる半径は `checkEnemyHit()` を二分探索して**実測**する。ウニが
  同じ向きに並んでいると二分探索が誤るので、1体ずつ残して測ります
- ゴール判定も本番と同じ式(`goalRadius - shipSize * 0.3`)
- START から幅優先でたどり、ゴール条件を満たす場所に届くか

泳ぐ敵は動きつづけるため、通行可否の判定からは外しています(待てば必ず
どく=道を塞ぎ続けることはない、という前提)。

### 通れる範囲の考え方(交差点で引っかからないように)

船は点ではなく半径 `shipSize` の円です。通路を1本ずつ `shipSize` だけ
痩せさせてその合併をとると、**通路どうしが交わる隅がごっそり欠けます**
(痩せさせてから合併 ≠ 合併してから痩せさせる)。本来なら船が収まる隅が
通れない扱いになり、交差点で引っかかる感触の原因になっていました。

`isPassable()` はまず従来どおりの速い判定(1本の通路だけで収まるか)を行い、
それが外れたときだけ**船の円周12点がどれかの通路の内側にあるか**を見ます。
これは「合併してから痩せさせた」領域の近似で、従来の判定より必ず広いので、
`gen-dsm-levels.mjs` が保証している到達性が壊れることはありません。

壁ずりは `slideStep()`(壁の法線から沿う向きを求める、従来方式)に加えて、
それでも進めないときに `SLIDE_ANGLES` で入力の向きを少しずつ回して通れる
向きを探します。交差点では法線がどちらの通路のものか紛らわしく、法線だけ
だと進める道があるのに止まることがあったための保険です。

`STEP_MAX` はコマ落ち対策の上限で、通常のフレームは1回で動かします。
ここを細かく刻むと壁ぎわを正確になぞる代わりに、交差点の細い隙間でいちいち
止まってしまい、**かえって引っかかる感触が強くなる**ので注意してください
(実測で「通り抜けられる向き」が増えても「途切れずに進めたフレーム」が
落ちました)。

ゲーム画面には `?dsmdebug=1` を付けて開くと、当たり判定の境界・船と
ゴールのヒットボックス・START座標・FPS・現在のワールド座標・カメラ座標が
表示されます（本番では無効）。

### 画像アセット

`dsm-goal-chest.png` はゴール地点(宝箱)の見た目に使っている画像です。
ユーザーから提供された宝箱イラストの一覧(スクリーンショット)から1点を
切り出し、背景の市松模様(透過を示す市松格子)を外周からの塗りつぶし探索で
検出して透明化したものです(宝箱本体の暗い部分を誤って透明にしないよう、
外周と連結している市松模様だけを対象にしています)。当たり判定は
従来どおり `stage.goalRadius` の円で行うため、この画像自体は見た目だけの
役割です。

### 探査船の描画

探査船もコードで描いています(デザイン案「⑪ソナー型」)。設計図は船体長
`SHIP_L=206`・半径 `SHIP_R=56` の座標系で、`drawShip()` が
`stage.shipSize × SHIP_UNIT` を縮尺にして貼ります。**当たり判定は従来どおり
`stage.shipSize` の円**なので、見た目を差し替えても操作感は変わりません。

左を向いたときだけ上下を裏返しています(`Math.cos(ang) < 0`)。こうしないと
ハッチとソナーが下向きになります。スクリューは `ship.propSpin` で回していて、
ジョイスティックの倒し具合に比例して速くなります。

### ウツボの描画(画像ではなくコード)

ウツボ(Stage31〜50)は画像を使わず `deep-sea-maze.js` の中で描いています。

| variant  | 見た目                     | ステージ    | 速さ     |
| -------- | -------------------------- | ----------- | -------- |
| `glow`   | 放射状エリマキウツボ       | Stage31〜40 | ゆっくり |
| `normal` | くねくね太骨ウツボ         | Stage41〜50 | 速い     |

見た目は `EEL_KINDS` の1オブジェクトにまとまっていて、色は `pal`、かたちは
`draw(c, ph)` が持っています。`ph` は 0〜2π の位相で、背骨のうねりと襟の
ゆれを同じ値から動かしているため、8コマできれいに1周します。

**開いた口の中は塗っていません。** 上あごと下あごの隙間は透明のままなので、
迷路の背景がそのまま透けます(歯だけが噛み合わせ線に残ります)。`eeHead()`
に口の中を塗る処理を足すと、この見え方が崩れるので注意してください。

勾配と影ぼかしを毎フレーム作り直すと重いので、`eelSheetFor()` が起動時に
**8コマぶんをオフスクリーンのキャンバスへ一度だけ焼き**、本番のループでは
`コマ番号 × セル幅` で切り出して貼るだけにしてあります。種類ごとに
`cellW` / `cellH`(余白を含む1コマの大きさ)・`span`(中身の長さ)・`offX`
(中身をセルの中央に寄せるずらし量)を持っていて、貼るときは
`swimmer.size × cellW / span` を幅にするので、**画面上の全長が
`swimmer.size` になります**。かたちを描き替えて大きさが変わったときは、
この3つを合わせて更新してください(焼き込み時にセル矩形でクリップして
いるので、はみ出すと切れます)。`EEL_BAKE_SCALE` はシートの解像度で、
上げると綺麗になるぶんメモリを食います。

元絵はどちらも頭が右向きなので、左へ泳ぐときだけ左右反転しています。

画面上の大きさは `gen-dsm-levels.mjs` の `size` で決まります
(エリマキウツボ 180 / 骨ウツボ 300)。骨ウツボは大きいぶん貼るときに
引き伸ばされてぼやけるので、`EEL_KINDS.normal.bake` で焼き込みの解像度
だけを上げてあります(既定は `EEL_BAKE_SCALE`)。
当たり判定も同じ `size` から作る(`checkEnemyHit()` が `size*0.4` を半長、
`size*0.1` を半径として使う)ので、**大きさを変えたら必ず `dsm-levels.js` を
作り直してください**。作り直さないと、見た目と当たり判定がずれます。
