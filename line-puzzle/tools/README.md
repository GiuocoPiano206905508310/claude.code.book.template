# ステージ生成・検証ツール

`levels.js`（本編50ステージ）と `ura-levels.js`（裏1〜30）は手書きではなく、
ここのスクリプトで生成・検証しています。裏ステージのCSS（もみじのマス絵と
金属光沢の選択ボタン）も生成物です。

## 1. 候補プールを作る（数分かかります）

```sh
python3 generate-pool.py pool.json
```

**正解の経路を先に引き、止めたい位置にお邪魔ブロックを置いていく逆算方式**で盤面を作ります
（`carve()`）。各手で「行けるところまで」ではなく途中で止めたい場合、その一つ先にブロックを
新設して停止理由を作ります。経路が通らなかったマスも最後にブロックへ変換します。
経路上でも停止理由でもないマスなので、変換しても経路は変わりません。

ランダムにブロックを置く方式も試しましたが、解ける盤面がほぼブロック0〜1個のものに偏り
（7x7で成功例の平均1.1個）、盤面がスカスカになるため採用していません。

作った盤面は改めて全解探索にかけ、難易度指標（マス数・ブロック数・迷いどころの数・
探索ノード数・解の総数）を記録します。数十秒で10万件規模のプールができます。

環境変数: `PER_SIZE`（盤面サイズごとの上限件数）、`BUDGET_SCALE`（時間予算の倍率）、
`P_LO`/`P_HI`（早期停止の確率＝ブロックの作られやすさ）。

## 2. 50ステージを選んで levels.js を書き出す

```sh
python3 build-levels.py pool.json ../levels.js
```

難易度スコアがなだらかに上がるよう50件を選びます。一本道の盤面とブロックが少なすぎる盤面は
候補から除き、終盤は迷いどころが3つ以上ある盤面だけを使います。書き出す前に全件を再生検証します
（新ルールで手順を再生して全マスが塗られるか、空振りの手が混ざっていないか、
盤面が連結しているか）。

## 2-b. 裏ステージ（裏1〜30）を作る

裏ステージは本編50ステージをすべてクリアすると解放される、石が点在する難しい盤面です。

```sh
python3 generate-scattered.py scattered.json     # 候補プール（数分かかります）
python3 build-ura-levels.py scattered.json ../ura-levels.js
```

`generate-pool.py` の `carve()` は「経路が通らなかったマスをまとめて石にする」ため、
石が一枚岩の壁になり、歩ける場所が細い通路に狭まります。石が多く見えても分岐が無いので、
見た目ほど難しくなりません。

そこで `generate-scattered.py` では**経路と石を同時に、後戻りありで探索**します。
各手は「行けるところまで進む」か「途中で止めて、その一つ先に石を置く」のどちらかで、
未通過のマスが分断された時点でその枝を捨てます（連結性の枝刈り）。取り残しのポケットが
生まれないので盤面は「経路 + 止まる理由の石」だけで埋まり、石は1〜2マスの粒として
散らばります。石がつながる数は `MAX_CLUMP`（既定2）までに制限しています。

作った盤面はより短い解が無いかを調べ、最短手順に置き換えてから記録します
（`minimise()`）。画面の「最短N手」を正しく出すためです。打ち切りに達した盤面は
`minproven` が false になり、`build-ura-levels.py` の候補から外れます。

環境変数: `PER_SIZE` / `BUDGET_SCALE` / `MAX_CLUMP` / `NODE_CAP` / `MIN_NODE_CAP`。

`build-ura-levels.py` は、石がまばら（孤立率45%以上・最大の塊2マス以下）で迷いどころが
多い候補だけから、難易度がなだらかに上がるよう30面を選びます。書き出す前に全件を
再生検証します。できあがりは 10x9〜12x11・石14〜28個・39〜59手で、本編（平均約20手）
よりはっきり長い盤面になります。

## 2-c. 裏ステージの見た目（もみじ・金属光沢）を作る

```sh
python3 gen-ura-style.py          # style.css を書き換える
python3 gen-ura-style.py --check  # ずれていれば終了コード1
```

`style.css` の「自動生成」マーカーで囲まれた範囲だけを差し替えます。マーカーの外は
手書きなので、この範囲に手で書き足さないでください。

* `momiji.py` … もみじの葉をSVGで組み立てます。極座標で葉の裂片と切れ込みをたどり、
  縁にぎざぎざを付け、上の葉ほど大きく下ほど小さくなるようにします。輪郭の先端と葉柄の
  先が正方形の角にちょうど触れるよう、縦横それぞれ引き伸ばして枠いっぱいに収めます。
  帯ごとの色は緑（裏1〜10）・黄（裏11〜20）・赤（裏21〜30）。
* `metal.py` … ステージ選択ボタンの縦縞クローム調グラデーションを作ります。同じ色相の
  明暗を12段に刻んだ `linear-gradient(90deg, ...)` です。

どちらも CSS の `data:image/svg+xml,...` として埋め込むため、追加の画像ファイルは
ありません。

## 2-d. アカウント（ログインと、ユーザーごとの保存）

進行状況はふだんこの端末の localStorage に置くだけだが、ログインするとアカウントにも
保存され、別の端末でも続きから遊べる。認証と保存は Supabase（給与・勤怠システムと
同じプロジェクト）を使う。

```sh
# Supabase の管理画面 → SQL Editor に貼って一度だけ実行する
cat supabase-setup.sql
```

`line_puzzle_progress` テーブル（1ユーザー1行・進行状況は jsonb）と、自分の行だけを
読み書きできる行レベルセキュリティ(RLS)を作る。anon キーは公開されるので、RLS が
無いと誰でも他人の記録を読めてしまう。

SQL のほかに、管理画面で2か所の設定が要る（SQLでは変えられない。詳しくは
`supabase-setup.sql` の冒頭に書いてある）。

* Authentication → Providers → Email の **Confirm email をオン**
  （新規登録の確認メールを出すため。オフだと登録した瞬間に入れてしまう）
* Authentication → URL Configuration → **Redirect URLs** に公開URLを登録
  （メールのリンクから戻ってくる先。登録が無いとリンクを開いてもゲームに入れない）

クライアント側は `../cloud.js`。supabase-js は 200KB あり、この一枚のゲームには
重いので使っていない。必要なのは「登録・ログイン・トークン更新・1行の読み書き」だけ
なので fetch で直接 REST を叩いている（`build-single-file.py` で1ファイルにまとめる
ときも、そのまま埋め込める）。

* 登録: ユーザー名 / メールアドレス / パスワード
* ログイン: メールアドレス + パスワード（メールが本人確認の宛先なので、
  パスワード再設定メールが使える。ユーザー名は画面に出す表示名）
* 新規登録すると確認メールが届き、そのリンクを開いて初めて登録が完了する。
  リンクは `…/line-puzzle/#access_token=…&type=signup` の形で戻ってくるので、
  `cloud.js` の `readAuthRedirect()` が読み取ってログイン状態にし、URLからは消す
* アカウント画面から**ユーザー名・メールアドレス・パスワード**を変えられる。
  ユーザー名はその場で変わる。メールアドレスは新しいアドレス宛の確認リンク、
  パスワードは登録アドレス宛の変更リンクを開いて初めて変わる
  （パスワードはメール経由なので、今のパスワードを覚えていなくても変えられる）
* 同じメールアドレスで2つ目のアカウントは作れない。Supabase が auth.users の
  メールアドレスを一意にしている。ただし確認メールを送る設定のときは、登録済みの
  メールでも Supabase は成功のような形で返す（他人のメールが登録済みかを外から
  調べられないため）ので、`identities` が空かどうかで見分けて案内している
* ログインしていない間の記録は、あとでログインした時にそのアカウントへ引き継ぐ
  （同じステージの記録が両方にあるときは、★が多いほう・同数なら手数が少ないほうを残す）
* 同じ端末で別のアカウントに切り替えても混ざらないよう、保存先の名前に
  ユーザーIDを付けている（`linePuzzle.progress.v1:<user id>`）

## 3. ブラウザで通しテストする

```sh
# リポジトリのルートで
python3 -m http.server 8777 --bind 127.0.0.1 &
node tools/test.mjs      # 要 playwright
```

登録不要で始められること、全50ステージの自動クリア、オートセーブと再開、
各ボタンの動作と配置、クリア後の再チャレンジ、★が黄色の塗りつぶしであること、
通過済みマスに戻れないこと、スワイプ操作、全ステージにお邪魔ブロックがあること、
行き止まりのお知らせ、チュートリアルの中身、アイコンが単色かどうかを確認します。

裏ステージについては、30面すべての再生検証と石のまばらさ、本編50ステージを
クリアするまで解放されないこと、解放後に遊べて記録が本編と別に残ることを確認します。

アカウントについては、本物の Supabase を叩かずに済むよう、認証と保存の2つの
エンドポイントだけを `page.route()` で肩代わりする偽のバックエンドを使います。
登録・ログイン・間違ったパスワード・ログイン前の記録の引き継ぎ・クラウドへの書き戻し・
別端末からの続き・クラウドが落ちている時をひと通り確認します。

確認メールの流れも通しで確認します。偽バックエンドが送ったメールを控えておき、
その `#access_token=…&type=…` を付けたURLを開くことで「メールのリンクを押した」を
再現しています。新規登録の確認、リンクを開く前はログインできないこと、同じメールで
2つ目を作れないこと、ユーザー名・メールアドレス・パスワードの変更までを見ます。

全ステージを実際に自動プレイするため、通しで8〜10分ほどかかります。

## 4. 版数(?v=)を付け直す ← 公開前に必ず

```sh
python3 stamp-assets.py          # 付け直す
python3 stamp-assets.py --check  # ずれていれば終了コード1
```

対象は `style.css` / `levels.js` / `ura-levels.js` / `cloud.js` / `game.js` です。

GitHub Pages は静的ファイルをブラウザにキャッシュさせるため、版数を付けずに更新すると
利用者には古い CSS/JS が読み込まれ続け、変更が反映されません。

手で番号を増やす運用は付け忘れます（このリポジトリでも過去に一度漏れています）。
そこで**ファイルの内容そのもののハッシュ**を版数にしています。中身が変われば版数も必ず
変わり、中身が同じなら版数も変わりません。`tools/test.mjs` でも版数と中身の一致を
確認しているので、付け忘れるとテストが落ちます。

## 5. 1ファイルにまとめて配布する

```sh
python3 build-single-file.py out.html --standalone   # 単体で開ける完全なHTML
python3 build-single-file.py out.html                # head を配布先が用意する形式（本文のみ）
```

CSS と JS をすべて埋め込むので、1枚のHTMLだけを置ける場所にそのまま配布できます。
